# Firebase setup

## V1.1 collections

V1.1 adds only Firestore documents under the existing user hierarchy:
`countdownStates` and immutable `countdownEvents`. It adds no Firebase project,
database, API, billing, Storage, or Cloud Function. Deploy the updated
`firestore.rules` and unchanged indexes through the existing short-lived CI
identity. Existing schema-1 medicines remain accepted; new writes use medicine
schema 2 with nullable, bounded per-slot countdown fields.

## No-cost gate

Before creating or enabling a resource, confirm all of the following:

- the Firebase project displays **Spark**;
- no Cloud Billing account is linked;
- only one Firestore database will be created;
- the database is **Standard edition**;
- no Cloud Functions, Cloud Storage, Realtime Database, Hosting, SQL Connect,
  Analytics, AdMob, Test Lab, or paid Google Cloud service is enabled; and
- the workflow does not offer or select **Upgrade**, **Blaze**, **Link billing
  account**, or a free-trial billing account.

Official references:

- Firebase pricing plans:
  <https://firebase.google.com/docs/projects/billing/firebase-pricing-plans>
- Firestore no-cost quota:
  <https://firebase.google.com/docs/firestore/quotas>
- Firebase App Distribution:
  <https://firebase.google.com/docs/app-distribution>
- Workload Identity Federation for deployment pipelines:
  <https://cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines>
- IAM pricing:
  <https://cloud.google.com/iam/pricing>

Firebase currently documents App Distribution and most Authentication options
as no-cost. Cloud Firestore has a limited free quota on Spark. If the free
Firestore quota is exhausted, the product stops serving the over-quota
operation until reset; never attach billing to work around it.

The read-only billing check is:

```text
https://console.cloud.google.com/billing/linkedaccount?project=meds-widget-ffelixq
```

It must report that the project has no linked billing account. Do not click a
link/upgrade action.

CI federation needs the IAM, Service Account Credentials, and Security Token
Service APIs:

```text
iam.googleapis.com
iamcredentials.googleapis.com
sts.googleapis.com
```

These identity prerequisites were enabled only after confirming billing was
disabled. Billing was checked again after enablement and remained disabled.
Google documents IAM API use as free. This does not authorize enabling unrelated
or paid APIs.

## Authenticate the Firebase CLI

Check first:

```bash
firebase login:list
firebase projects:list
```

If no usable account is present:

```bash
firebase login
```

Allow the CLI to open the browser. If the localhost callback cannot complete,
cancel safely and run:

```bash
firebase login --no-localhost
```

Follow only the URL generated by the CLI. Never paste a Google password,
refresh token, access token, service-account key, or recovery code into a
terminal transcript, issue, commit, or chat.

## Create or select the project

Use a shell variable that is not a system-reserved name:

```bash
MEDS_FIREBASE_PROJECT="meds-widget-ffelixq"
firebase projects:list
firebase projects:create "$MEDS_FIREBASE_PROJECT" --display-name "Meds Widget"
```

If `projects:list` already shows the intended project, do not create a
duplicate. Associate the local folder:

```bash
firebase use --add
```

Select the exact project and use a clear alias such as `default`. `.firebaserc`
contains project identifiers, not credentials, and may be committed once the
real project is confirmed.

Observe and record the project:

```bash
firebase projects:list
firebase use
```

Then open:

```text
https://console.firebase.google.com/project/meds-widget-ffelixq/settings/general
```

Confirm the project ID/number and **Spark** plan. Recheck the Cloud Billing URL
above before enabling Firestore.

## Create the Firestore database

The required location is `asia-southeast1`, which Firebase lists as Singapore:
<https://firebase.google.com/docs/firestore/locations>.

The location can be difficult or impossible to change. Inspect the command
before confirming:

```bash
firebase firestore:databases:create '(default)' \
  --location=asia-southeast1 \
  --project "$MEDS_FIREBASE_PROJECT"
```

The Firebase CLI creates Standard edition unless Enterprise options are
explicitly selected. Do not pass Enterprise, PITR, backup, clone, TTL, CMEK, or
MongoDB-compatible options; some of those require billing.

If the CLI cannot create the default database, use:

```text
https://console.firebase.google.com/project/meds-widget-ffelixq/firestore/databases
```

Select exactly:

- **Create database** / **Add database**
- **Standard edition**
- database ID **(default)**
- location **asia-southeast1 (Singapore)**
- **Production mode**
- **Create**

Do not choose Test mode with permissive rules. Do not create a second database.
The official management guide is
<https://firebase.google.com/docs/firestore/manage-databases>.

After creation, verify the database card reports Standard and Singapore before
writing data.

## Add debug and release SHA fingerprints

Google sign-in needs the fingerprints for every signing identity that will run
the release package.

### Debug

```bash
./gradlew signingReport
```

Under the app's debug variant, copy both SHA-1 and SHA-256. The debug variant
uses the same application ID as release, so both debug and release certificate
fingerprints belong on the one registered Firebase Android app.

### Release

Using the ignored release keystore:

```bash
keytool -list -v \
  -keystore release-signing/meds-widget-release.p12 \
  -alias <RELEASE_ALIAS>
```

Enter the password interactively. Do not put it on the command line, in shell
history, or in documentation.

### Register

For each SHA-1/SHA-256:

```bash
firebase apps:android:sha:create \
  1:648847295725:android:15e7b95037f6ff897678e4 \
  <SHA_FINGERPRINT> \
  --project "$MEDS_FIREBASE_PROJECT"
```

Verify:

```bash
firebase apps:android:sha:list \
  1:648847295725:android:15e7b95037f6ff897678e4 \
  --project "$MEDS_FIREBASE_PROJECT"
```

The same fingerprints can be added under **Project settings → General → Your
apps → SHA certificate fingerprints**:


## Obtain `google-services.json`

After enabling Google and adding every SHA fingerprint, generate a fresh
configuration:

```bash
firebase apps:sdkconfig ANDROID \
  1:648847295725:android:15e7b95037f6ff897678e4 \
  --project "$MEDS_FIREBASE_PROJECT" \
  > app/google-services.json
```

Confirm locally without printing the file:

```bash
test -s app/google-services.json
git check-ignore app/google-services.json
git ls-files --error-unmatch app/google-services.json
```

Expected:

- `test` succeeds;
- `git check-ignore` names the file; and
- `git ls-files --error-unmatch` fails because it is not tracked.

The config must contain a generated web OAuth client so the Google Services
plugin creates `default_web_client_id`. If Google sign-in reports that it is not
configured, enable Google/add SHAs first and download the file again.

Firebase API keys in this file identify the project; they are not the security
boundary. Nevertheless, this repository deliberately ignores the real file and
reconstructs it in CI from an encrypted secret. Firestore Authentication and
Security Rules enforce authorization.

Never commit:

- `app/google-services.json`;
- a service-account JSON file;
- Firebase CLI login state or tokens;
- tester email lists; or
- Firebase emulator export data.

## Deploy rules and indexes

Run emulator rules tests first:

```bash
npm ci --prefix firebase-tests
npm test --prefix firebase-tests
```

Inspect the deployment:

```bash
firebase deploy \
  --only firestore:rules,firestore:indexes \
  --project "$MEDS_FIREBASE_PROJECT"
```

The tracked `firebase.json` Firestore section points only to:

```text
firestore.rules
firestore.indexes.json
```

The file also records the intended Auth provider metadata used by Firebase
tooling, but the deployment command is explicitly limited to Firestore and does
not deploy provider configuration. It does not configure Hosting, Functions,
Storage, Realtime Database, Data Connect, or Analytics. A deployment must not
be expanded beyond the two tracked Firestore resource files.

After deployment, open:

```text
https://console.firebase.google.com/project/meds-widget-ffelixq/firestore/rules
https://console.firebase.google.com/project/meds-widget-ffelixq/firestore/indexes
```

Confirm:

- the deployed rules require authentication and UID ownership;
- there is no `allow read, write: if true`;
- the active-medicine composite index is ready; and
- history uses the automatic single-field `syncedAt` index.

## App Distribution

Firebase documents App Distribution as no-cost:
<https://firebase.google.com/docs/app-distribution>.

Open:

```text
https://console.firebase.google.com/project/meds-widget-ffelixq/appdistribution
```

Select the `io.github.ffelixq.medswidget` Android app and **Get started** if
shown. Create the group with CLI:

```bash
firebase appdistribution:group:create "Owners" owners \
  --project "$MEDS_FIREBASE_PROJECT"
```

Add the Firebase account's email without committing it:

```bash
firebase appdistribution:testers:add \
  --group-alias owners \
  <TESTER_EMAIL> \
  --project "$MEDS_FIREBASE_PROJECT"
```

Do not save `<TESTER_EMAIL>` in the repository. If it cannot be determined from
the authenticated Firebase account, request it only when this step is reached.

A one-off signed APK upload looks like:

```bash
firebase appdistribution:distribute \
  app/build/outputs/apk/release/app-release.apk \
  --app 1:648847295725:android:15e7b95037f6ff897678e4 \
  --groups owners \
  --release-notes-file <IGNORED_RELEASE_NOTES_FILE> \
  --project "$MEDS_FIREBASE_PROJECT"
```

Use APK distribution. App Distribution AAB delivery can require Google Play
linkage, which is out of scope. The CLI returns a Firebase console URI, tester
URI, and a signed one-hour binary download URI. Never print or record that
short-lived signed URI in a public log or `VALIDATION_REPORT.md`; record only
appropriate durable identifiers/links.

Official CLI guide:
<https://firebase.google.com/docs/app-distribution/android/distribute-cli>.

## CI configuration

The real `google-services.json` is encoded locally without printing it and
stored only on the main-restricted GitHub environment `production` as
`GOOGLE_SERVICES_JSON_BASE64`. Do not create a repository-level duplicate. On
macOS, a safe pattern is:

```bash
base64 -i app/google-services.json |
  gh secret set GOOGLE_SERVICES_JSON_BASE64 \
    --repo ffelixq/meds-widget \
    --env production
```

On Linux:

```bash
base64 -w 0 app/google-services.json |
  gh secret set GOOGLE_SERVICES_JSON_BASE64 \
    --repo ffelixq/meds-widget \
    --env production
```

The release keystore and passwords use
`ANDROID_RELEASE_KEYSTORE_BASE64`,
`ANDROID_RELEASE_KEYSTORE_PASSWORD`, `ANDROID_RELEASE_KEY_ALIAS`, and
`ANDROID_RELEASE_KEY_PASSWORD`, also only in `production`. CI must authenticate
to Google with the active short-lived Workload Identity Federation setup:
project-number-scoped pool `meds-widget-github`, provider `meds-widget-main`,
immutable GitHub repository ID `1315914252`, repository-owner ID `167162073`,
and exact ref `refs/heads/main`. The `production` environment contains
`GCP_WORKLOAD_IDENTITY_PROVIDER` and `GCP_DEPLOY_SERVICE_ACCOUNT`, and has no
`FIREBASE_DEPLOY_SERVICE_ACCOUNT_JSON` fallback secret.

The deployment service account has exactly
`roles/firebaserules.admin`, `roles/datastore.indexAdmin`,
`roles/firebaseappdistro.admin`, and
`roles/serviceusage.serviceUsageConsumer` at project scope. It has no
`roles/firebase.viewer` or Firestore document-read role. A dedicated JSON key
is documented only as an emergency fallback—not a personal Firebase CLI
token—and would have to use the same least privileges. See
[CI/CD](CI_CD.md) for the complete variable/secret contract and rotation
procedure. The successful run linked above verified that Firebase CLI consumed
WIF-provided Application Default Credentials and skipped its JSON fallback.
The temporary user-managed service-account key was deleted afterward; zero
user-managed keys remain.

Never expose deployment secrets to pull requests from forks. Deployment is
allowed only after all validation jobs succeed on `main`.

## Account deletion limitation

V1 deletes data from the Android client because Cloud Functions are forbidden.
It reauthenticates, iteratively deletes the four known subcollections, deletes
the root user document, and deletes the Authentication user. A graph-wide
operation gate waits for any admitted medicine/dose/settings/widget mutation and
rejects new ones before deletion begins. The UI remains on a blocking deletion
surface until the graph restarts.

After Authentication deletion, the app independently attempts to clear every
local settings/widget DataStore, update all widgets to signed-out state,
terminate Firestore, and call `clearPersistence()`. It rebuilds `AppGraph` and
restarts the `MainActivity` task even if one of these now-best-effort local
cleanup actions fails.

This operation:

- requires connectivity and a recent credential; its collection queries use
  `Source.SERVER`, so a cached empty collection cannot be mistaken for complete
  server deletion;
- is not atomic across Firestore batches and Authentication;
- may leave partial data if the device/process stops or quota is exhausted;
- knows only the subcollections enumerated in the current app; and
- must be updated if the schema gains another collection.

The Firebase SDK call logically removes its persistent cache after the active
instance has terminated. It is not a secure-overwrite API and does not guarantee
that physical storage blocks are unrecoverable on a rooted or compromised
device. A local cleanup error cannot restore the already-deleted Authentication
account. On a shared/high-risk device—or after a reported best-effort cleanup
failure—clear Android app data after deletion.

The user can retry while the Authentication account still exists. If auth
deletion succeeded after a partial Firestore failure, project-owner cleanup may
be required. No document should claim the client flow is a server-side
recursive delete.
